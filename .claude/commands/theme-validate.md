# 테마 수혜주 교차 검증

`$ARGUMENTS`로 주어진 테마 키워드에 대해 `app.py`의 밸류체인 분석 파이프라인을 실행하고,
도출된 추천 후보 종목들이 아래 4대 가이드라인을 충족하는지 하나씩 비판적으로 검증한다.
이 명령어는 `app.py` 자체의 GPT 호출 결과를 다시 한번 **사람이 감사하듯** 검토하는
2차 검증 레이어이자, `app.py`의 `WORKAROUND_REASON_PHRASES` 같은 **문구 기반 필터가
표현을 바꿔 우회하는 것까지는 못 잡는 구조적 한계를 메우는 의미 기반 검증 레이어**다.
`app.py`가 이미 15% 급등 필터, KRX 종목코드 검증, 우회 문구 필터를 거쳤더라도, 그 필터를
통과했다는 사실 자체를 그대로 신뢰하지 말고 매번 직접 재확인할 것.

인자가 비어 있으면 사용자에게 테마 키워드를 물어보고 중단한다.

## 검증 가이드라인

1. **밸류체인 근거의 명확성** — 단순히 이슈와 이름이 함께 언급되는 "테마 엮임"이 아니라,
   실제 소재/부품/장비 밸류체인 상의 구체적인 공급·고객·경쟁 관계에 근거하는가? 특히
   그 기업이 이슈의 대상(원자재/부품/서비스)을 실제로 **외부에 판매하는 공급자**인지,
   아니면 그것을 **매입해서 쓰는 구매자**일 뿐인지 반드시 구분한다. 완제품 제조사가
   자기 제품에 쓸 원료를 자체 조달/내재화하는 것은 "판매"가 아니다. 확신이 서지 않으면
   WebSearch로 해당 기업의 실제 사업 부문(무엇을 만들어 누구에게 파는지)을 확인한다.
2. **정밀도 유지(급등 종목 배제)** — 이미 15%(또는 실행 시 사용한 임계값) 이상 급등한
   대장주·종목이 추천 목록에 섞여 있지 않은가?
3. **논리적 연결고리** — OpenAI 분석이 제시한 "근거" 텍스트가 이슈 → 해당 기업의 매출/수주/
   실적으로 이어지는 구체적 인과 경로를 설명하는가, 아니면 "관련이 있다"는 식의 막연한
   주장에 그치는가?
4. **우회 논리 탐지(표현이 아니라 의미 기준)** — `app.py`는 근거 텍스트에 "불구하고",
   "그럼에도" 같은 **특정 문구**가 있으면 코드로 자동 제외하지만, 이는 정확히 같은 단어를
   썼을 때만 걸러지는 결정론적 필터라 표현만 바꾸면 통과한다(예: "오르지만",
   "상승하는 가운데", "부담이 있으나" 등). 그러므로 상태가 "추천 후보"로 이미 앱을
   통과한 종목이라도 **문구와 무관하게** 다음 패턴이면 의미상 우회 논리로 판단해 FAIL
   처리한다: 근거 문장이 (a) 이슈로 인한 부정적 영향(원가 상승·비용 부담 등)을 먼저
   인정한 뒤, (b) 그 이슈와 직접 연결되지 않는 별개의 긍정적 사유(예: "고부가가치
   제품군 판매 증가", "프리미엄 수요 증가", 전반적 업황 호조)를 근거로 수혜를 주장하는
   구조. 이 경우 "app.py의 문구 기반 필터가 놓친 사례"로 명시적으로 표시한다.

## 절차

1. **분석 실행** — 프로젝트 venv(`.venv/Scripts/python.exe`)로 `app.py`의 파이프라인
   함수를 직접 호출해 `$ARGUMENTS` 테마에 대한 최신 결과를 JSON 파일로 저장한다
   (터미널 출력은 한글 인코딩이 깨질 수 있으니 반드시 파일로 저장 후 Read 도구로 읽을 것).
   `.env`에 `OPENAI_API_KEY`가 없으면 여기서 실패하므로, 그 경우 사용자에게 알리고 중단한다.

   ```bash
   ./.venv/Scripts/python.exe -c "
   import json, sys
   import app

   issue = sys.argv[1]
   data = app.get_valuechain_from_llm(issue)
   lead = data['lead_stock'].strip()
   graph, node_meta = app.build_valuechain_graph(data)
   df = app.collect_node_price_data(node_meta, lead, 10, 15)

   clean_df = df.drop(columns=['hop']).astype(object).where(df.notna(), None)
   out = {
       'issue': issue,
       'theme': data.get('theme', issue),
       'lead_stock': lead,
       'rows': clean_df.to_dict(orient='records'),
   }
   with open('.claude/tmp/theme_validate_result.json', 'w', encoding='utf-8') as f:
       json.dump(out, f, ensure_ascii=False, indent=2)
   print('DONE')
   " "$ARGUMENTS"
   ```

   (`.claude/tmp` 디렉터리가 없으면 먼저 생성한다.)

2. **결과 로드** — Read 도구로 `.claude/tmp/theme_validate_result.json`을 읽는다.
   `상태`가 "추천 후보"인 행만 검증 대상으로 삼는다. ("제외-이미급등", "미확인 종목",
   "미분류(그래프 연결 없음)" 상태는 이미 걸러진 것이므로 가이드라인 2 관점에서만
   간단히 재확인하고 본 검증에서는 제외)

3. **종목별 판정** — "추천 후보" 상태인 각 종목에 대해 G1~G4를 모두 판정한다 (앱이 이미
   "추천 후보"로 분류했다는 사실 자체를 신뢰하지 말고 처음부터 다시 판단할 것):
   - **가이드라인 1**: `단계`와 `근거` 텍스트를 보고, 실제 그 기업이 이슈 대상을 판매하는
     공급자인지 구매자일 뿐인지 비판적으로 검토한다. 확신이 서지 않으면 WebSearch로
     교차 확인한다.
   - **가이드라인 2**: `등락률(%)`이 임계값 미만인지 직접 재계산 확인한다.
   - **가이드라인 3**: `근거` 문장이 구체적 인과 경로를 담고 있는지 판정한다.
   - **가이드라인 4**: 근거 문장을 "부정적 영향 인정 → 무관한 사유로 수혜 주장" 구조인지
     의미 기준으로 재검토한다. `app.py`의 `WORKAROUND_REASON_PHRASES`(현재 "불구하고",
     "그럼에도")에 걸리지 않았더라도 이 구조면 FAIL이며, 그 경우 사유에 "app 필터 미탐지"
     라고 명시한다.

   종목마다 PASS / WARN / FAIL과 한 줄 사유를 매긴다. 4개 가이드라인 중 하나라도 FAIL이면
   종합 판정은 FAIL이다. "제외-근거 논리 불충분(우회 표현)" 상태로 이미 앱이 제외한
   종목도 1~2개 표본으로 스팟체크해 앱의 판단이 정확했는지 간단히 확인한다.

4. **보고서 출력** — 다음 형식의 마크다운 표와 요약을 작성한다:

   | 종목명 | 종목코드 | G1(밸류체인) | G2(정밀도) | G3(논리성) | G4(우회논리) | 종합 판정 | 사유 |
   |---|---|---|---|---|---|---|---|

   마지막에 통과/경고/탈락 종목 수를 요약하고, G4에서 "app 필터 미탐지"로 잡힌 사례가
   있다면 별도로 강조한다. FAIL 종목이 있다면 왜 `app.py`의 추천 목록에서 빠져야 하는지,
   그리고 `VALUECHAIN_SYSTEM_PROMPT`나 `WORKAROUND_REASON_PHRASES`(app.py) 중 어느
   부분을 보강할 수 있는지 제안하되, 표현 패턴을 무한정 키워드로 추가하는 방식은
   "-지만"처럼 일반적인 한국어 접속 어미와 겹쳐 오탐을 유발할 수 있으므로 신중히
   판단할 것 — 이 4번째 가이드라인(의미 기반 검증) 자체가 그 한계를 보완하기 위한
   장치임을 감안한다.
